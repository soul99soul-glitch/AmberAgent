# 鸿蒙 UI 迁移：参考包与持续执行方案

状态：准备方案，等待 Android 收尾提交。日期：2026-09-13。

目标：让公司电脑上的鸿蒙工程逐批采用 Android 收尾版的页面设计，保留鸿蒙已有功能和数据契约，每批可运行、可对照、可恢复。

本次只调查 Android 仓库并整理计划。尚未读取鸿蒙仓库内容、验证公司电脑的编译/设备环境，也未启动鸿蒙修改、长期目标或自动化。当前工作区仍有收尾改动，本文与附录中的源码数值和行号均为候选参考，不能代替最终提交。

用户补充的公司端目标是 [amber-harmony-preview](https://github.com/soul99soul-glitch/amber-harmony-preview)，报告远端跟踪为 `amber-harmony/harmony-preview`、提交为 `5ca32d491d61b9e099b522ce115408896c8f1015`。这些由公司端重新核对，规划机未独立验证该远端提交；用户明确要求在公司电脑执行。Android 本机核实的 origin 是 `https://github.com/soul99soul-glitch/AmberAgent.git`，分支为 `main`，最终参考 SHA 仍待用户收尾。

## 1. 推荐的交付方式

把工作拆成两个明确产物：

1. **Android 参考包**：固定一个提交，带上设计来源、原生截图、关键交互录像、页面和状态清单、相关 UI 源码及素材。
2. **鸿蒙执行目录**：公司电脑上的任务读取参考包，对应到真实鸿蒙文件，维护待办、验证记录和下一步；持续按页面族推进。

不需要把几十个页面的全部细节塞进一次提示词。总说明只管目标、优先级和完成条件，具体页面按需读取。也不需要先建设专门的任务调度平台。

配套文件：

- `PAGE_INVENTORY.md`：Android 候选页面、入口和容易遗漏的嵌套界面。
- `DESIGN_REFERENCE.md`：当前设计来源与局部覆盖；最终提交后复核。
- `START_TASK.md`：可复制给公司电脑上鸿蒙任务的完整启动说明；先读这一份即可开工准备。

## 2. 收尾提交后固定基线

| 字段 | 正式参考包需要记录的内容 | 当前状态 |
| --- | --- | --- |
| Android 基线 | 用户指定的最终提交完整 SHA | 待收尾提交；不自动采用移动中的 HEAD |
| 构建来源 | 构建变体、版本、APK SHA-256、是否有影响 UI 的工作区差异 | 待基线构建 |
| 视觉环境 | 设备/模拟器、逻辑宽高、像素密度、系统字号、语言、主题/主题包 | 待逐组截图登记 |
| 截图来源 | 页面 ID、状态 ID、构建 ID、采集时间、测试数据版本 | 已有历史图，尚未绑定最终基线 |
| 鸿蒙工程 | 公司电脑的真实仓库、分支、起始提交与现有 WIP | 待公司端核对 |
| 运行方式 | 实际可用的构建、安装、启动、导航、截图命令 | 待公司端核对；不凭空填写命令 |

Android 提交后，从该提交导出参考源码，或从它建立独立只读参考副本。不要清理正在收尾的工作区来凑一个“干净版本”。如果构建还包含影响 UI 的未提交改动，先记录差异，不能把截图冒认成该 SHA 的产物。

提交之后不用立刻把所有图重拍一遍：先检查旧图与最终源码的相关差异，变化过的页面及公共组件消费者重新采集；旧图只有在能够证实适用时才升为基线参考。仅看文件时间较新不足以证明版本一致。

后续 Android 再变更时单列增量，明确是否升级参考版本；已在执行的批次继续使用原基线，避免目标漂移。

## 3. 给足设计参考的最小内容

建议最终参考包使用以下结构；这是待制作的结构，本次没有伪装成已经导出完成：

```text
android-ui-reference-<sha>/
  BASELINE.md                 # SHA、构建、采集环境、适用范围
  DESIGN.md                   # 语义颜色、字号、间距、圆角、阴影、动效
  PAGES.md                    # 页面/嵌套界面清单和参考索引
  COMPONENTS.md               # 少量现有公共组件及实际消费者
  ASSETS.md                   # 图标、字形、字体、插图来源及许可证
  source/                    # 保留仓库相对路径的 UI 源码和必要依赖
  assets/                    # 实际使用的图标、字体、品牌资源
  screens/<page-id>/          # 原生静态图及状态说明
  motion/<flow-id>/           # 仅关键交互的短录像及操作顺序
  prototypes/                # 旧 HTML，逐页标注适用/过时/示例
```

源码和素材要实际放进包里，或由公司电脑直接读取固定提交；不能只写本机绝对路径。历史 `app/build/`、`/tmp/` 截图同样需要复制，防止构建清理或换电脑后丢失。按必要范围导出，不打包登录数据、真实会话数据库和凭据。

### 参考冲突怎样处理

首先遵守用户已明确确认的具体设计决定。日常复刻以**同一基线的 Android 实屏和实际源码**互相核对：截图给最终视觉，源码解释尺寸、层级、状态和动效。两者冲突时查清版本、配置与状态，不盲选一个。

历史 HTML 只在对应页面未被后续修改、且与基线一致时作为补充。iOS 是本次 Android 设计的背景，当前鸿蒙迁移的直接目标仍是选定 Android 版本，避免混用两个不断变化的目标。

当前已确认的特别注意事项：

- 历史文档记录过首页单独确认的样式，但当前收尾源码已继续变化；首页必须按最终确认与基线单独对照，不能照搬旧例外或其它页面的规则。
- 2026-09-13 的后续修改涉及控件尺寸、聊天字号、聊天时间线与子代理状态栏。初版 HTML/截图可能没有这些变化。
- 现有覆盖报告记录的是 81 份 HTML 原型，其中有弹层、输入态和示例；这个数字不是 81 个独立路由，也不是鸿蒙待改页面总数。
- 原型的假键盘、固定成功结果、演示账号/模型/文章，不是应移植的业务能力。

### 每页至少包含什么

| 内容 | 需要回答的问题 |
| --- | --- |
| 页面与入口 | 从哪里进入、需要什么实体参数、返回到哪里？ |
| 主参考 | 对应哪个基线、主题、逻辑尺寸、状态的截图？ |
| 页面结构 | 顶栏、滚动区、固定底栏、浮层的关系是什么？ |
| 样式 | 用哪些语义 token/组件，哪些是本页局部覆盖？ |
| 行为 | 点击、长按、滑动、展开、编辑、保存/取消分别发生什么？ |
| 数据状态 | 正常/空/加载/失败/选中等哪些真实存在、会影响布局？ |
| 验收 | 鸿蒙端必须比较哪些图、实际操作哪些路径？ |

共享规则写一次，每页只补差异。不要给不存在的状态编写实现要求。

### 截图和录像的投入

每个纳入范围的页面至少有一张主状态图；会改变布局或行为的关键状态另补图。共享组件先覆盖浅色、深色、窄屏/大字号，再对高风险页面补充验证，不机械地对所有页面穷举主题、字号和状态的笛卡尔积。

聊天重点补空会话、普通消息、生成中、思考展开、工具/审批、键盘与底部状态栏；设置重点补即时保存、弹层编辑、长标题、禁用行；其它页面按实际风险选取。短录像用于路由转场、底部弹层、长按/滑动、流式滚动等静态图解释不了的行为。

统一测试内容和尽量一致的逻辑视口后并排比较。Android 的 dp/sp 和鸿蒙的布局/字体单位不能只按物理像素机械替换；系统字体、行高、安全区和键盘需要目标平台实测。系统权限、系统分享、文件选择等系统界面以平台规范适配；应用自有外观与信息层级保持一致。

## 4. 在公司电脑上先做一次入口盘点

公司端任务先核对鸿蒙已有页面和导航，建立 **Android 参考 → 鸿蒙实际实现 → 处理方式** 的映射，同时反查鸿蒙已有但 Android 清单未覆盖的页面。以应用入口、tab、sheet/dialog、参数化详情和深层编辑器为口径，不能只按文件名搜索 `Page`。

处理方式分为：已有页面改样式、多个 Android 界面对应同一鸿蒙容器、鸿蒙平台替代、缺少功能依赖、目标独有页面待归类。缺少功能先登记具体依赖及影响，继续其它页面；不要擅自扩张成完整功能移植，也不能把缺失项算完成。

在同一次盘点中跑通一条最小链：构建 → 安装 → 启动 → 打开一个页面 → 截图。若只能编译，后续可以先做不依赖设备的工作，但整批视觉验收要保持待验证。公司端的 SDK、项目脚本和工具可用性以当地实测为准。

## 5. 分批迁移顺序

| 阶段 | 内容 | 完成后得到什么 |
| --- | --- | --- |
| A：基线与环境 | 固定参考包、鸿蒙双向页面映射、最小构建/运行/截图链 | 清楚改哪些页面，以及如何证明改对 |
| B：样板与公共组件 | 首页、设置首页、提供商详情/编辑、聊天主路径；按依赖顺序推进 | 校准品牌页面、卡组、表单/弹层、复杂消息流四类范式 |
| C：设置页面族 | 外观/显示、模型/Provider、记忆、扩展/权限等同类页面 | 复用已校准的公共样式，收敛局部覆盖 |
| D：会话与内容 | 历史/搜索/收藏、看板/深读、资料/统计 | 列表、搜索、阅读和数据可视化一致 |
| E：复杂工作区 | Novel、技能/扩展编辑、小应用、议会 | 编辑、跨 tab 状态与参数化详情闭环 |
| F：平台及辅助界面 | 运行环境、系统权限、WebView 壳、备份、日志/调试等 | 明确能力对应与平台差异 |
| G：全局收尾 | 回查所有入口/嵌套界面，执行关键端到端流程 | 页面和行为都有证据，剩余缺口清楚 |

阶段分类允许公司端根据实际工程调整；已有样板页从后续批次排除，避免重复计数。常规批次建议 3–6 个相近页面，聊天或 Novel 可以独立成批，不按固定页数强拆状态耦合。

先校准少量公共组件，再批量替换页面。样板阶段适合用户看一次整体方向，但不默认增加“每改三页必须等批准”的硬停顿。已经有明确参考时，任务可自行验收并继续。

时间估计在样板完成后给出：分别记录简单列表、表单/弹层、复杂工作区的实际实现和验证耗时，再估剩余工作。当前没有鸿蒙源码和运行条件，不虚报“几小时完成全部页面”。

## 6. 让任务持续运行并可恢复

在鸿蒙仓库放一个小目录即可：

```text
docs/ui-migration/
  PLAN.md          # 当前执行范围、固定基线、真实命令、批次与完成定义
  TASKS.md         # 唯一任务清单：页/状态、目标文件、依赖、状态、证据
  PROGRESS.md      # 简短追加记录：做了什么、核实什么、下一步
  DECISIONS.md     # 只记影响后续的设计决定和平台例外
  evidence/       # 鸿蒙截图、对照图、必要日志/录像
```

状态用 `pending → in_progress → implemented → verified` 即可；有具体阻塞时标记 `blocked` 并写依赖。`implemented` 只代表代码完成，不能冒充截图和行为已验证。平台例外单列理由及确认依据，不能自行跳过后宣称全量完成。

每个工作单元按这个顺序执行：

1. 读取当前任务清单、相关决策、上次进度，核对实际 Git diff。中断后先核实已有实现，不能仅按旧状态重做或覆盖。
2. 选取依赖已满足的一小批页面。只读取这些页面需要的源码、图和状态说明。
3. 修改对应鸿蒙 UI，保留真实数据、权限、导航和保存契约。
4. 跑最小充分构建/定点测试，运行到实际页面，按相同状态截图并与基线共同查看。
5. 修正可见偏差，验证核心交互和状态；记录截图、命令结果和仍未覆盖的项目。
6. 更新任务状态和下一步，检查本批 diff；有未阻塞的待办就继续。公共组件再改时回查直接受影响的已完成页面，不重跑无关全量测试。

任务清单至少保留这些列：ID、页面/子状态、参考文件、鸿蒙入口/文件、依赖、状态、验证证据、阻塞原因。进度必须能回答“哪个页面的哪个状态已验证”，不要只写“完成 70%”。

例如首页任务卡可这样填，实际路径和参数由公司端补齐：

```text
ID: HOME-01
状态: pending
目标: 会话首页及新会话入口与固定 Android 基线一致
Android 来源: SessionHomePage.kt + HomeSessionIcons.kt + 对应基线截图
鸿蒙入口/文件: 待从真实路由定位
依赖: Android 基线、首页主状态图、公共文本/卡片/图标规范
必看状态: 无会话、有会话、置顶/继续项、真实存在的加载/错误态
必验操作: 搜索、新会话、进入/返回会话、现有置顶与删除交互
视觉重点: 顶部搜索与日期、卡片阴影、最终基线的会话图标与强调色规则、消息数、新会话胶囊
数据约束: 继续使用实际会话列表与回调；不从原型复制固定数据
证据: 鸿蒙同状态截图、并排对照、关键动作验证结果
下一步/阻塞: 待填具体事实
```

Git 检查点按公司端已有授权执行。若已授权本地提交，可每个验证完的批次提交一次；未授权时保留可审阅 diff 与记录，不把等待提交当作 UI 工作阻塞。保护既有 WIP，不混入他人修改，不自动推送、发布或清数据。

### 如何挂成长任务

在公司电脑的目标仓库任务中，使用可用的 Codex 持续目标功能，并把目标指向上述文件。官方将 `/goal` 用于跨轮次推进有明确验证终点的迁移/重构，建议定义目标、证据和检查点。[OpenAI 官方说明：Follow a goal](https://learn.chatgpt.com/use-cases/follow-goals)。公司端具体入口与可用性需要当地确认，本次没有替它改设置或创建目标。

长期目标负责当前工作持续推进，磁盘记录负责恢复。主机休眠、执行环境不可用、额度或必要权限受阻时，仍可能中断；“持续目标”不等于承诺无人值守永久运行。恢复后重新核对记录和工作区即可继续。

若以后明确需要跨天唤醒，再在公司端配置相应自动化，继续同一个目标和任务目录。不要为了长任务启动多个互相覆盖的独立执行者。当前准备阶段无需设置定时器。

可独立的页面族可以委派，但公共 token/组件和导航各有唯一写入负责人，构建安装与设备操作统一调度。不要多个代理同时操作同一模拟器。优先用少量边界清楚的分工，不能用并发数量代替验收。

## 7. 什么才算完成

每页同时满足：入口可达；自有 UI 与选定参考的结构、文字层级、颜色、间距、组件和关键动效相符；核心动作仍触发真实行为；相关状态有记录；无明显截断、重叠、键盘遮挡或返回异常。

编译和截图之外，重点验证：编辑/取消与持久化是否保持原行为、输入中间态不被强制格式化、点击和长按区域是否退化、列表/流式消息是否还能正常滚动、切换主题和返回后状态是否正确。仅视觉变化不要求顺手重测全部网络服务；涉及 Provider、账户或远端功能时明确区分本地状态演示和真实调用证据。

整个目标完成必须满足：

- 双向页面清单中所有纳入范围的项都有结论；遗漏页面、阻塞项和例外单独列出，不能隐入完成数。
- 必改项全部达到 `verified`，或用户已明确接受相应范围调整。
- 鸿蒙构建、运行与关键业务流程有证据；最终 diff 只包含授权范围。
- 对照图和可安装产物可交付，记录明确标出设备、网络/账号等未验证层级。

现阶段交付的是规划和 Android 候选参考索引。正式参考包的封版依赖即将到来的 Android 提交；真正开工还依赖公司电脑上的鸿蒙工程和运行条件核对。
